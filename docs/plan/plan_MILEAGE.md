# План MILEAGE

## Файлы

- `backend/config/rules.php` — добавить в секцию `vehicle` конфигурируемый порог пробега для перевода заявки в `review`, не изменяя лимит валидации `max_mileage_km`.
- `backend/src/Domain/DecisionEngine.php` — принять порог пробега в зависимостях, расширить сигнатуру `decide()` нормализованным пробегом и применить правило только для пробега выше порога и LTV не более `85.0`.
- `backend/src/Domain/AssessmentService.php` — передать в `DecisionEngine` нормализованный `$input['mileage']` после валидации.
- `backend/src/AppFactory.php` — передать новый порог из конфигурации в конструктор `DecisionEngine` для HTTP-приложения.
- `tests/Unit/DecisionEngineTest.php` — адаптировать создание движка к новой зависимости и добавить проверки влияния пробега на решение.
- `tests/Unit/AssessmentServiceTest.php` — адаптировать создание движка и проверить передачу пробега из сервиса в расчёт решения после успешной валидации.
- `tests/Unit/ApplicationValidatorTest.php` — покрыть допустимые границы диапазона, значения вне диапазона, пустой и неизвестный пробег как ошибки валидации.

## Шаги

1. Добавить отдельный порог `400000` км в `vehicle` конфигурации; существующий `vehicle.max_mileage_km = 500000` оставить лимитом допустимого входного значения.
2. Расширить `DecisionEngine`: получить порог из конфигурации, принять пробег вторым аргументом `decide()` и при пробеге строго больше `400000` км вернуть `review` только если LTV не более `85.0`. Для пробега не более `400000` км сохранить текущие LTV-решения. Не определять результат сочетания пробега более `400000` км и LTV более `85.0`.
3. В `AssessmentService` передать в расчёт решения уже проверенный и нормализованный `$input['mileage']`; для невалидного пробега сохранить прекращение расчёта на валидации.
4. Проверить и при необходимости скорректировать `ApplicationValidator`, чтобы допустимыми были только числовые значения от `0` до `500000` км включительно, а пустой или неизвестный пробег не запускал расчёт решения.
5. Обновить сборку зависимостей в `AppFactory` и в unit-тестах для новой зависимости и сигнатуры `DecisionEngine`.
6. Добавить и выполнить unit-тесты для REQ-MILEAGE-01—REQ-MILEAGE-04 и AC-MILEAGE-01—AC-MILEAGE-08 без теста, задающего исход конфликтного случая из Open question.

## Тесты

- REQ-MILEAGE-01 / AC-MILEAGE-01: при `mileage = 399999` для каждого текущего LTV-результата (`approve`, `review`, `reject`) решение остаётся определённым LTV и не меняется из-за пробега.
- REQ-MILEAGE-01 / AC-MILEAGE-02: при `mileage = 400000` для каждого текущего LTV-результата (`approve`, `review`, `reject`) решение остаётся определённым LTV и не меняется из-за пробега.
- REQ-MILEAGE-02 / AC-MILEAGE-03: при `mileage = 400001` и LTV не более `85.0` заявка получает `review`.
- REQ-MILEAGE-03 / AC-MILEAGE-04: при `mileage = 0` валидация проходит и расчёт решения может быть выполнен.
- REQ-MILEAGE-03 / AC-MILEAGE-05: при `mileage = 500000` валидация проходит и расчёт решения может быть выполнен.
- REQ-MILEAGE-03 / AC-MILEAGE-06: при `mileage = -1` и при `mileage = 500001` валидация не проходит и решение не рассчитывается.
- REQ-MILEAGE-04 / AC-MILEAGE-07: при пустом значении `mileage` валидация не проходит и решение не рассчитывается.
- REQ-MILEAGE-04 / AC-MILEAGE-08: при неизвестном пробеге без числового значения валидация не проходит и решение не рассчитывается.
- Не добавлять тест, который ожидает `review` или `reject` при `mileage > 400000` и LTV `> 85.0`: этот исход не определён спецификацией.
- После реализации выполнить `make test` и `make lint`.

## Риски

- Open question из спецификации остаётся открытым: для пробега `> 400000` км и LTV `> 85.0` не определено, вернуть `review` или `reject`. План не выбирает и не тестирует ни один из результатов.
- `max_mileage_km = 500000` — это валидационный максимум, а не новый порог решения: его снижение до `400000` превратит случаи `400001–500000` из `review` в ошибку валидации, что противоречит задаче.
- Пустое либо неизвестное значение пробега должно останавливаться на валидации, а не превращаться в числовой пробег и не получать решение; фактические представления таких значений нужно сверить с контрактом входного payload при реализации.
- Изменение конструктора или сигнатуры `DecisionEngine` требует обновить все места создания и вызова, включая `AppFactory` и unit-тесты; иначе приложение или тесты завершатся ошибкой типов/числа аргументов.
- Перенесённые Open questions спецификации о цели изменения и сознательно исключённом объёме остаются без ответа; план не выводит из них дополнительных работ.
