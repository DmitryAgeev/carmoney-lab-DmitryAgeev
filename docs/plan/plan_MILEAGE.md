# План MILEAGE

## Файлы

- `backend/config/rules.php` — добавить в секцию `vehicle` конфигурируемый порог пробега для перевода заявки в `review`, не изменяя лимит валидации `max_mileage_km`.
- `backend/src/Domain/DecisionEngine.php` — принять порог пробега в зависимостях, расширить сигнатуру `decide()` нормализованным пробегом и применить правило решения согласно подтверждённому приоритету.
- `backend/src/Domain/AssessmentService.php` — передать в `DecisionEngine` нормализованный `$input['mileage']` после валидации.
- `backend/src/AppFactory.php` — передать новый порог из конфигурации в конструктор `DecisionEngine` для HTTP-приложения.
- `tests/Unit/DecisionEngineTest.php` — адаптировать создание движка к новой зависимости и добавить проверки влияния пробега на решение.
- `tests/Unit/AssessmentServiceTest.php` — адаптировать создание движка и проверить передачу пробега из сервиса в расчёт решения и нулевой `approved_limit` при `review`.
- `tests/Unit/ApplicationValidatorTest.php` — добавить проверку отсутствующего `mileage` как ошибки валидации.

## Шаги

1. Зафиксировать с заказчиком приоритет правила пробега относительно LTV `> 85%`; без этого нельзя однозначно определить результат конфликтной заявки.
2. Добавить отдельный порог `400000` км в `vehicle` конфигурации; существующий `vehicle.max_mileage_km = 500000` оставить лимитом допустимого входного значения.
3. Расширить `DecisionEngine`: получить порог из конфигурации, принять пробег вторым аргументом `decide()` и для значения строго больше `400000` вернуть `review` в месте, соответствующем согласованному приоритету.
4. В `AssessmentService` передать в расчёт решения уже проверенный и нормализованный `$input['mileage']`.
5. Обновить сборку зависимостей в `AppFactory` и в unit-тестах для новой зависимости `DecisionEngine`.
6. Добавить и выполнить unit-тесты правила пробега, его границ, сохранения LTV-поведения и валидации отсутствующего пробега.

## Тесты

- Отдельно проверить, что при низком LTV пробег ниже или равный порогу сохраняет `approve` и запрошенную сумму в `approved_limit`.
- Граничное значение: `mileage = 399999` — правило пробега не переводит заявку в `review`; при низком LTV ожидается `approve`.
- Граничное значение: `mileage = 400000` — правило пробега не переводит заявку в `review`; при низком LTV ожидается `approve`.
- Граничное значение: `mileage = 400001` — заявка проходит текущую валидацию и получает `review`; `approved_limit = 0`.
- Граничное значение: пустой/отсутствующий `mileage` — `ApplicationValidator` выбрасывает `ValidationException` с ошибкой поля `mileage`; решение не рассчитывается.
- Сохранить существующие проверки LTV, включая `85.0` (`review`) и `85.01` (`reject`), если только подтверждённый приоритет правила пробега не определит исключение для комбинации с пробегом более `400000` км.
- После реализации выполнить `make test` и `make lint`.

## Риски

- В текущей постановке не определён конфликт: для пробега `> 400000` и LTV `> 85%` возможны разные ожидаемые результаты — `review` как безусловное правило либо сохранение `reject` как более строгого решения.
- `max_mileage_km = 500000` — это валидационный максимум, а не новый порог решения: его снижение до `400000` превратит случаи `400001–500000` из `review` в ошибку валидации, что противоречит задаче.
- Отсутствующий пробег уже преобразуется в `-1` и отклоняется валидатором; правило решения не должно заменять эту ошибку на `review`.
- Изменение конструктора или сигнатуры `DecisionEngine` требует обновить все места создания и вызова, включая `AppFactory` и unit-тесты; иначе приложение или тесты завершатся ошибкой типов/числа аргументов.
- Не входит: изменение схемы БД и репозитория, API-контрактов, фронтенд-формы, исторических заявок, расчёта LTV, правил возраста и `ltv_by_age`.
